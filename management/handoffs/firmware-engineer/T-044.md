## Library and core lines (SOURCE)
- **F-005, what `touched()` returns on a NACK.**
  - `Adafruit_MPR121.cpp` `touched()`: `uint16_t t = readRegister16(MPR121_TOUCHSTATUS_L); return t & 0x0FFF;`
  - `Adafruit_BusIO_Register.cpp:188-191`: `uint32_t Adafruit_BusIO_Register::read(void) { if (!read(_buffer, _width)) { return -1; }`
  - `Adafruit_I2CDevice.cpp` `_read`: `if (recv != len) { … return false;`
  - So on a NACK or a short read, `read()` returns 0xFFFFFFFF and `touched()` returns **0x0FFF: all 12 pads touched**. The old code would have sent 12 Note Ons on a lost sensor.
  - The sketch no longer calls `touched()`. It reads the 2 status bytes itself with `readRegisters()` and checks the transaction result.
- **F-006, AVR I2C clock.**
  - `avr/1.8.8/libraries/Wire/src/Wire.cpp:56-64`: `void TwoWire::begin(void) { … twi_init();`
  - `utility/twi.c:94`: `TWBR = ((F_CPU / TWI_FREQ) - 16) / 2;`, with `utility/twi.h`: `#define TWI_FREQ 100000L`
  - `Wire.cpp:85-87`: `setClock` → `twi_setFrequency(clock)`
  - `Adafruit_I2CDevice.cpp:30-31`: `bool Adafruit_I2CDevice::begin(bool addr_detect) { _wire->begin();`
  - So every `sensors[s].begin()` re-ran `twi_init()` and put a Leonardo back to 100 kHz after `setup()`'s `setClock(400000)`. The review finding is confirmed.
  - On rp2040, `Wire.cpp:119-122` shows `begin()` returning early when `_running`, and `setClock` (`Wire.cpp:111-115`) applies `i2c_set_baudrate` while running, so the RP builds were not affected.
  - Fix: `I2C_BUS.setClock(400000)` right after every `begin()` in `startSensor()`, on all cores. The `setup()` call is kept.

## Changes (firmware/FrutaMIDI)
- **`fm_notes.h` (new): `PadNotes<N>`.**
  - Per-pad note, pressure and last-sent value. The reference count is the number of pads holding a note.
  - Note On on 0 → 1 only; Note Off on 1 → 0 only, preceded by AT 0 if a value above 0 was sent.
  - Shared-note aftertouch = max of the holders' pressures, with the same ±2 / floor filter as before.
  - A new holder inherits the value already sent for the note.
  - The note is one channel (MIDI_CHANNEL), so counting per note is counting per channel.
- **`fm_sensor_health.h` (new): `SensorHealth`.**
  - 3 consecutive failed transactions → lost.
  - An ECR read-back every 250 ms; a value other than the one read after start-up means the chip reset itself (it still ACKs) → lost at once.
  - Retry when more than 2000 ms have passed since the last start attempt. This covers a lost sensor and a second sensor that was missing at boot.
- **`fm_mpr121.h`**: adds `MPR121_REG_TOUCHSTATUS = 0x00` and `mpr121_touch_bits()` (mask 0x0FFF, same as the library).
- **`FrutaMIDI.ino`**:
  - `activeNote`/`lastPressure`/`sensorOk` are replaced by `pads` and `health[]`; `SENSOR_RETRY_MS` moved to the header.
  - `startSensor(s)` = `begin()` → `setClock(400000)` → `configureSensor()` → ECR read → `health.started()`.
  - `sensorLost(s)` releases that sensor's 12 pads. The loop retries each sensor independently.
  - The burst read (`readSensorData`) also reports to `health`.
  - The LED shows the existing fast error blink (100 ms) while any sensor is lost or missing. Blink sequences still take priority.

## Numerical findings (value unit LABEL)
- **Size delta vs T-041/T-043** (MEASUREMENT): rpipico std flash +504 bytes, RAM +44 bytes; leonardo flash +530 bytes, RAM +40 bytes.
- **Extra I2C traffic per loop** (CALCULATION, 400 kHz, data bytes only):
  - The status read is the same 2-byte transaction `touched()` made, so there is no change.
  - The ECR check adds 4 bytes ≈ 90 µs every 250 ms per sensor.
- **Detection time** (CALCULATION):
  - A NACKing sensor is declared lost after 3 loops.
  - A chip that reset itself is declared lost within 250 ms (the next ECR check).
  - The first retry is up to 2000 ms after the last start attempt, then every 2000 ms (host stub: lost at 1002 ms, retried at 2001 and 4002 ms).

## Assumptions
- A real lost sensor NACKs or returns a short read. This is the BusIO behaviour quoted above; on real hardware it needs a hardware test.
- After a spontaneous reset the MPR121 ECR reads 0x00. That is the reset value; datasheet S-006 is not quoted here.
- The host `healthsim` copies the loop's call order (retry → status → health → ECR check → pad step → LED). A static test checks that the sketch calls the same functions.

## Open decisions for manager
1. The retry period is measured from the last start attempt, not from the moment of loss. A sensor lost more than 2 s after its last start is therefore retried on the next loop. Is that acceptable, or should the retry wait 2 s after the loss?
2. When the chip resets itself, its notes are released by the normal touch path (it reports no touches) before the ECR check marks it lost. Only one Note Off is sent either way.
3. Systems T-012 should state the REQ-009 behaviour: 3 failed transactions or a wrong ECR → release, error blink, retry > 2 s.
