## Findings (sampler defects and observations; nothing fixed, docs/ untouched)
- **FINDING-SW-2 (medium, defect):** learn mode accepts a note that another pad already uses, with no warning. Both pads then show the same note, and `findIndex` always picks the lower pad, so the other pad can no longer be reached from MIDI. Measured: pad 0 learns 37, and note 37 then flashes only pad 0. Test: "FINDING-SW-2 …". Suggested fix (manager to decide): swap the notes of the two pads, or clear the old pad's note. This is not trivial UX policy, so I did not fix it.
- **FINDING-SW-1 (low):** MIDI notes that arrive before the "Clica para ativar o som" click are logged but give no sound and no pad flash, because playPad returns early when ctx is null. A user can think the controller is not working. Suggestion: flash the pad anyway, or show a status hint. Test: "FINDING-SW-1 …".
- **OBS-SW-3 (info):** the sampler is omni and accepts all 16 channels. Whether the firmware channel should be filtered is open; INTERFACES.json has no MIDI interface yet.
- **OBS-SW-4 (info):** pads are one-shot. Note Off does not stop pad sounds, and aftertouch on pad notes is visual only (the bar). Aftertouch opens the filter only for synth voices, which matches the help text.
- **OBS-SW-5 (info, not tested):** a busy device is not retried on a later statechange. The page tells the user to reload, which matches the code (the input-id key does not change).

## Not covered
- Real Web MIDI with real hardware, the browser permission prompt, and real Windows busy-driver behaviour. The busy path is stubbed as `open()` rejecting with InvalidAccessError; this is an ASSUMPTION about how Chrome signals a busy port, to be checked on Windows with a DAW holding the port.
- Audible output, levels and latency. Only Web Audio graph calls are observed, and audio is muted.
- Drag-and-drop sample loading and decodeAudioData, the volume slider, pointer clicks on pads (only the keyboard fallback is covered), Edge, Windows, layout and theme, and the path where localStorage is unavailable.

## Assumptions
- MIDIMessageEvent is stubbed as `{data: Uint8Array}`; the page reads only `e.data`.
- Chrome fires a statechange when a port opens. The stub reproduces this to exercise the page's guard against re-binding.
- The tests describe the current implementation, because no interface is frozen yet. The FINDING tests describe present behaviour and must be updated when the findings are fixed.
