## Open decisions for the manager

1. **D-1, latency and jitter targets.** The sensor sets a 4 ms floor, so a 1 ms jitter target cannot be met with option A. Options:
   - Keep 10 ms worst case and 1 ms jitter, and accept FAIL.
   - Change to 10 ms worst case for C ≤ 100 pF with M1 applied, which is still 10.25 ms, so it is marginal.
   - Set ≤ 15 ms worst case and drop the jitter target.
   This also needs the user's view, because the 1 ms jitter came from my reading of the literature, not from the definition.
2. **D-2, ESD protection on the electrodes (REQ-023).** Either add a series resistor per electrode (and optionally a TVS) on the PCB, which needs electronics analysis against the MPR121 charge time, or accept the risk and document it.
3. **D-3, 24 pads.** Either keep them breadboard-only (the PCB has one socket), or add a second module footprint, which would be hard to fit on 100 × 70 mm.
4. **D-4, wrong-hole short (REQ-024).** Either change the S/J1 arrangement so that no GND hole is reachable by the 3V3 wire (for example separate hole rows per revision, or a jumper header), or accept the risk with the existing warning.
5. **D-5, I2C clock.** Either keep 400 kHz and add a physical rise-time measurement, or move to 100 kHz, which is in spec for up to 142 pF and costs about 0.5 ms per `touched()`.
6. **D-6:** which macOS versions are in scope for REQ-011.
7. **D-7, BOM target.** Confirm 25–30 EUR, and which items count. The core BOM straddles the target; prices from a named supplier are needed.
8. **D-8, language of user-facing UI and silkscreen** ("OITAVA", "ESCALA", sampler UI). Should it be English like all project files, or localised for Portuguese end users?
9. **Architecture ADR:** I recommend option A, with B kept as a research spike only and C rejected (`reports/systems/architecture_options.md`).
10. **Tooling:** approve installing a PDF text tool (for example pypdf into .venv), so that the Pico datasheets can be read and the ASSUMPTIONs on board current and regulator replaced by SOURCE values.
